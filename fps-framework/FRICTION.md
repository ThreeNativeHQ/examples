# Friction ledger — fps-framework

Kept while building, newest rows appended at the bottom of each block. "Evidence" points at
the file, command output, or screenshot that shows the problem.

| API or surface | What blocked the build | Workaround | Evidence |
| --- | --- | --- | --- |
| `InputMap` (`@threenative/core`) | No relative pointer delta and no pointer-lock helper anywhere in the input surface. `input.raw.pointer.position` is an absolute canvas point, which cannot drive an FPS look axis. Nothing in `AGENTS.md` covers mouse look. | Wrote a `MouseLook` class on raw `document` `mousemove` + `requestPointerLock` inside `src/entities/FpsPlayer.ts`, guarded by `typeof document === "undefined"`. This is exactly the DOM reach the "Keep the game portable to native" section forbids, so first-person look is web-only in this build. | `src/entities/FpsPlayer.ts:22-72`; `node_modules/@threenative/core/dist/game-DRt1Qhq3.d.ts:60-92` is the whole input API |
| `RigidBody3D` (`@threenative/physics`) | `IRigidBody3DOptions` has no `position`; it takes `object: Object3D` only. `Area3D` in the same file *does* take `position`, so the asymmetry reads as an oversight. Static level collision boxes have no mesh of their own (my walls are one mesh each but the yard's colliders are AABBs). | Allocate a throwaway `new Object3D()` per static body purely to carry a transform. | `src/scenes/Play.ts:86-116`; `node_modules/@threenative/physics/dist/Area3D-CvwDbfU6.d.ts:337-350` |
| `CharacterBody3D.moveAndSlide` | The solved transform is written to the mesh *after* the frame, not inside the call. Measuring `mesh.position` either side of `moveAndSlide` in the same frame yields ~0 every frame, so an odometer built the obvious way reports zero forever. Nothing fails: `typecheck`, the scene, and the HUD all look right. | Compare against the previous frame's written position instead of bracketing the call. | Failing assertion: `state.distanceMoved` after = `0` while the harness measured the subject moving `5.600` units (`TN_PLAYTEST_RESOURCE_STATE_STAGNATED`); fix at `src/entities/FpsPlayer.ts:157-166` |
| Playtest step vocabulary | `AGENTS.md` says "Steps count frames, not milliseconds — `holdFrames`, `waitFrames`". Those keys are accepted by the schema but **do not advance the fixed-step clock**: a 198-tick scenario advanced the game by 11 ticks (0.18 s), so 2 of 3 keypresses never became `justPressed` and `KeyW` moved the player 0.001 m. `playtests/survives.playtest.json` — the file the same document tells you to keep — uses `holdTicks`/`waitTicks`, which work. | Use `holdTicks`/`waitTicks` everywhere and ignore the documented spelling. | `/tmp/pt.json`: `frames: 258`, `timeRemaining` 59.4 → 59.2, `movement.distance 0.0011`. Same scenario with `holdTicks`: 5.60 m, 3 shots, 1 reload |
| Playtest resource assertions | Supported keys are `allowTrivial, anyOf, atSteps, changed, equals, gte, id, path, textIncludes, throughoutSteps` — there is no `lte`/`lt`. A countdown clock cannot be asserted to have gone *down*, only to have changed. | Asserted `changed: true` and checked the direction by eye in the JSON result. | `TN_PLAYTEST_SCENARIO_INVALID: Unknown key 'lte' at assert.resources[5].lte` |
| Vite dev server + playtest runner | The runner writes `artifacts/playtest/*` **inside the project**, and the scaffolded `vite.config.ts` sets `server.watch.usePolling: true` with no ignore list. The watcher sees those writes and full-reloads the page mid-scenario; the runner then fails the whole run with `TN_PLAYTEST_PAGE_NAVIGATED` and blames the game ("Remove the navigation from the game"). Two runs were lost to this before the cause was clear. | Added `server.watch.ignored: ["**/artifacts/**", "**/screenshots/**", "**/playtests/**"]`. | `vite.config.ts:6-14`; `/tmp/pt4.json` diagnostics |
| `AnimationPlayer` (`@threenative/core`) | `play(name, { fade })` is the entire API: no loop mode, no clamp-at-end, no "finished" event. A death animation therefore loops forever, and a one-shot fire clip cannot be sequenced back to idle by the framework. | Held the ragdoll by stopping mixer updates with `ctx.after(1.1, …)` and drove weapon clip selection from my own state machine each frame. | `src/entities/Enemy.ts:197-214`; `node_modules/@threenative/core/dist/index.d.ts:9-26` |
| Asset introspection | Nothing in `ctx.assets` or the tooling reports a loaded model's bounds, axis convention, or clip list, and the capture harness prints only console *errors*, so a `console.info` measurement never reaches the terminal. Placing the shipped viewmodel was blind guessing: the first two attempts put a 1.4 m rifle either through the camera or shrunk to a toy. | Wrote `measure.mjs`, a standalone Node script that parses the `.glb` with `GLTFLoader` and prints the bbox and clip names. It needs three DOM shims (`self`, `createImageBitmap`, `URL.createObjectURL`) before `GLTFLoader` will run under Node at all. | `measure.mjs`; output `size 0.573,0.392,1.394 centre -0.002,0.050,0.407 / clips Walk,Run,Reload,Shoot,Idle`; `screenshots/viewmodel-raw.png` shows the blind attempt |
| `ctx.raycast()` | Documented as "how you pick geometry under the pointer" with a `{ screen }` option, but the units of `screen` are undocumented (canvas pixels? NDC?) and there is no way to cast an arbitrary world ray — which is what a hitscan weapon is. It also returns only the nearest hit, so an occlusion test that must ignore thin dressing (target plates) cannot use it. | Used plain `THREE.Raycaster` for both the shot and the enemy's line-of-sight test, against an explicit object list. | `src/scenes/Play.ts:131-152`; the `IRaycastOptions` type says only "Screen point in canvas pixels. Defaults to the current pointer position." |
| `ctx.raycast()` / whole-scene picking | Raycasting "the whole scene" is unusable in first person: the viewmodel is a child of `ctx.camera`, which is added to the scene, so every shot hits your own rifle at 0.3 m. | Maintained an explicit `hittable` array of yard meshes, target plates and the enemy proxy. | `src/scenes/Play.ts:131-134` |
| Scene collapse / static batching | The renderer logs `TN_SCENE_COLLAPSE` decisions ("fewer than 200 meshes so far; still watching") on every boot. There is no documentation of what collapsing does to a mesh's raycastability or to `userData` carried on it — which matters when picking is how scoring works. I could not find out, so I never crossed the 200-mesh line to test it. | None; noted as an unknown. | `artifacts/playtest/console.json` |
| Starter `playtests/*.json` vs the brief | The starter's own scenario asserts against resource id `GameState`, the brief's sealed proof reads id `state`. Nothing in `AGENTS.md` mentions either. Only reading the compiled runtime shows both ids are registered for the same object. | Verified in `node_modules/@threenative/core/dist/playtest.js` and used `state`. | `stateResources()` returns `[["GameState", value], ["state", value]]` |
